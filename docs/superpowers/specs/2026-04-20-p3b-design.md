# P3b — Read-Only Dashboard + SSE Live-Tail

**Status:** Approved
**Date:** 2026-04-20
**Author:** gambtho (brainstormed with Claude)

## Overview

P3b adds the read-only operator dashboard to CronFoundry: a React SPA embedded in the Go binary, secured by the P3a session layer, covering overview stats, repos, schedules, run history, and per-run detail with SSE live-tail for in-flight runs.

## Scope

**In scope:**
- Vite + React + TypeScript SPA, embedded via `embed.FS`
- Five dashboard pages (Overview, Repos, Schedules, Runs, Run Detail)
- Six `/api/*` REST endpoints + one SSE endpoint
- SSE live-tail for in-flight runs
- shadcn/ui + Radix + Tailwind component library

**Out of scope:**
- Write surfaces (pause/resume, run-now, secrets, repo connect) — P3c
- Dark mode, keyboard shortcuts, responsive mobile layout — deferred
- TypeScript codegen from Go structs — hand-maintained types for MVP

## Architecture

The React bundle is built by Vite and embedded into the Go binary via `embed.FS`, served at `/` from `cmd/cronfoundry/serve.go`. A new `internal/webapi` package hosts all browser-facing endpoints under `/api/*`, secured by the P3a session middleware (`RequireSession`). The React app is a SPA with React Router v6; TanStack Query manages all server state. The SPA catches all non-`/api/*`, non-`/oauth/*`, non-`/internal/*` routes and returns `index.html`.

## Pages

Left-nav sidebar navigation with five pages:

### Overview (default landing page after login)
Summary cards in two groups:

**Operational health:**
- Schedules enabled / paused
- Runs today (count)
- Failures in last 24h
- Last run time (most recent across all schedules)

**Cost:**
- Tokens used today
- Cost this week
- Cost this month

Below the cards: a "Recent runs" table showing the last 10 runs across all schedules (schedule name, status badge, started_at, duration, cost).

### Repos
List of connected `repo_connection` rows. Columns: owner/name, default branch, last synced at, last synced SHA (truncated), sync error (if any).

### Schedules
All schedules + their parent skill names, grouped by repo. Each row: skill path, schedule name, cron expression, timezone, provider/model, status badge (enabled / paused / never-run), last run time, last run status.

Skills are not a separate page — they are surfaced inline within the Schedules view.

### Runs
Paginated run history table. Query parameters: `schedule_id`, `status`, `limit`, `offset`. Columns: schedule name, fire reason (schedule/manual), status badge, started at, duration, tokens in/out, cost, error (if any). Clicking a row navigates to Run Detail.

### Run Detail
Header row: run ID, schedule name, status, fire reason, started at, duration, tokens in, tokens out, cost, writeback commit SHA (if present).

Destination results section: one row per destination with type, status (ok/fail), HTTP status code, and destination-specific metadata (issue URL for github-issue, etc.).

Timeline section: scrollable list of `run_event` rows (ts, level, event_type, payload summary). For in-flight runs, this section is live-tailed via SSE (see below).

## API Endpoints

All routes under `/api/*`, all requiring session auth via `RequireSession` middleware. All queries scoped to `org_id` from the session.

```
GET /api/overview
  Response: { health: { schedulesEnabled, schedulesTotal, runsToday, failuresLast24h, lastRunAt },
              cost: { tokensToday, costThisWeekCents, costThisMonthCents } }

GET /api/repos
  Response: RepoConnection[]

GET /api/schedules
  Response: { repoId, repoOwner, repoName, schedules: Schedule[] }[]

GET /api/runs?schedule_id=&status=&limit=50&offset=0
  Response: { runs: Run[], total: int }

GET /api/runs/{id}
  Response: Run + RunEvent[] (all events for the run, including publish.* events used
  to render destination results in the UI — no separate destination-results query)

GET /api/runs/{id}/events  (SSE)
  — see SSE section
```

## SSE Live-Tail

`GET /api/runs/{id}/events` is a Server-Sent Events endpoint.

**Server behavior:**
1. Verify session auth and org ownership of the run. Return 403 if not authorized.
2. Flush all existing `run_event` rows for the run immediately as `data:` events (one JSON object per event).
3. If run is already in a terminal status (`succeeded`, `failed`, `partial_failure`), send `event: done\ndata: {}\n\n` and close.
4. Otherwise, poll `run_event` every 500ms for rows with `id > last_seen_id`. Stream each new row as a `data:` event.
5. After each poll, check `run.status`. When terminal, send `event: done\ndata: {}\n\n` and close.

**Client behavior:**
- Run Detail page opens `EventSource` to this endpoint when `run.status === 'running'`.
- Each `data:` event appends a row to the timeline list.
- On `event: done`, close the `EventSource` and trigger a TanStack Query refetch of the run detail (to update header: final status, duration, cost).
- If run is already terminal when the page loads, the SSE endpoint closes immediately after flushing history — no special client handling needed.

## Frontend Stack

| Concern | Choice |
|---|---|
| Build tool | Vite |
| Framework | React 18 + TypeScript |
| Routing | React Router v6 (SPA, client-side) |
| Server state | TanStack Query v5 |
| SSE | Native `EventSource` API (not TanStack Query) |
| Components | shadcn/ui on Radix UI primitives |
| Styling | Tailwind CSS |
| TypeScript types | Hand-maintained, matching Go API response shapes |
| Bundle embedding | `//go:embed all:web/dist` in `cmd/cronfoundry/serve.go` |

The Go server returns `index.html` for all GET requests that are not prefixed with `/api/`, `/oauth/`, or `/internal/`. This enables React Router's client-side navigation.

## Static Bundle Packaging

`/web` directory at repo root contains the Vite project. Build output goes to `web/dist/`. The Go binary embeds `web/dist` at compile time:

```go
//go:embed all:web/dist
var webFS embed.FS
```

The `serve` command registers a catch-all handler that serves from `webFS`, falling back to `index.html` for unmatched paths (SPA routing support).

`make build` runs `cd web && npm run build` before `go build` so the embedded bundle is always fresh.

## Testing

- **Go:** handler unit tests for each `/api/*` endpoint using `httptest` + `internal/testdb`. SSE endpoint tested with a client that reads until `event: done`.
- **Frontend:** Vitest for pure logic (query key helpers, type guards). No E2E browser tests in P3b — the existing `e2e_test.go` covers the serve path; UI correctness validated manually.

## Success Criteria

An operator can:
1. Log in via GitHub OAuth (P3a).
2. See the overview page with health and cost summary.
3. Navigate to Schedules and see all configured skills/schedules from their connected repo.
4. Navigate to Runs and filter by schedule or status.
5. Click a completed run and see its full event timeline.
6. Click an in-flight run and watch events stream live until the run completes.
