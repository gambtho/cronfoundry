# P4b/c — Bicep IaC + CI/CD

**Status:** Approved
**Date:** 2026-04-20
**Author:** gambtho (brainstormed with Claude)

## Overview

P4b/c moves CronFoundry from "runs on my laptop with docker-compose" to "one-command Azure deploy." It delivers a single Bicep template, two GitHub Actions workflows (PR gate + release), and a fully self-bootstrapping first-run story.

## Scope

**In scope:**
- `deploy/main.bicep` — subscription-level Bicep deploying all Azure resources into a dedicated resource group
- `deploy/params.example.json` — self-hoster parameter template
- `deploy/README.md` — operator setup guide (GitHub App registration, deploy steps, upgrade path)
- `ci.yml` — PR gate: build, test, vet, lint, Docker build check
- `release.yml` — tag-triggered: multi-arch Docker build + GHCR push + GitHub release with IaC artifacts attached
- Self-bootstrapping startup (auto-migrate + seed default org)

**Out of scope:**
- `azd` wrapper — pure Bicep + `az` CLI is sufficient for MVP
- Bicep modules split — single file for MVP
- `az deployment what-if` CI gate — deferred; requires Azure service principal in CI
- Azure Front Door / WAF — deferred; Container Apps managed TLS cert is sufficient for MVP
- Helm / AKS deploy path — deferred
- Multi-cloud (AWS, GCP) — deferred

## Azure Resources

Subscription-level deployment creates resource group `rg-cronfoundry-{env}` and all resources within it.

| Resource | SKU / Config | Notes |
|---|---|---|
| Resource Group | — | `rg-cronfoundry-{env}` |
| Container Apps Environment | Consumption | VNet-integrated |
| Container App `cronfoundry` | 0.5 vCPU, 1 GB, min 1 replica | Public ingress, TLS via managed cert |
| Container Apps Job `runner` | 1 vCPU, 2 GB | Manual-trigger type; dispatched by scheduler |
| Postgres Flexible Server | B1ms burstable | Private DNS zone, no public endpoint |
| Key Vault | Standard | Purge-protect on, soft-delete 90d |
| Log Analytics Workspace | 30d retention | Container Apps built-in log routing |
| Managed Identity `cf-serve` | — | Assigned to Container App |
| Managed Identity `cf-runner` | — | Assigned to Container Apps Job |

### Role Assignments (wired in Bicep)

| Identity | Role | Scope |
|---|---|---|
| `cf-serve` | Key Vault Secrets Officer | Key Vault |
| `cf-serve` | `Microsoft.App/jobs/executions/write` (Container Apps Jobs executor) | Runner Job |
| `cf-serve` | Postgres contributor (Entra auth) | Postgres Flexible Server |
| `cf-runner` | None | — (communicates with API only via JWT bearer) |

`cf-runner` has no Azure role assignments. It receives all credentials and context from the `/internal/*` API endpoints, authenticated via the per-run JWT issued by `cf-serve`.

## Parameters

Self-hoster copies `deploy/params.example.json` to `deploy/params.json` (git-ignored) and fills in values.

```json
{
  "env": "prod",
  "location": "eastus",
  "imageTag": "v0.1.0",
  "postgresAdminPassword": "<set this>",
  "githubAppId": "<your GitHub App ID>",
  "githubAppPrivateKeyBase64": "<base64-encoded PEM>",
  "githubOAuthClientId": "<your GitHub OAuth client ID>",
  "githubOAuthClientSecret": "<your GitHub OAuth client secret>",
  "adminLogins": ["your-github-username"],
  "allowedOrgSlugs": []
}
```

The Bicep template writes secret parameters (`postgresAdminPassword`, `githubAppPrivateKeyBase64`, `githubOAuthClientSecret`) directly into Key Vault during provisioning. The Container App reads them at startup via managed identity — they never transit Postgres or appear in Container App environment variables in plaintext.

Non-secret parameters (`githubAppId`, `githubOAuthClientId`, `adminLogins`, `allowedOrgSlugs`) are passed as Container App environment variables directly.

## Bicep Structure

Single file `deploy/main.bicep` with a `targetScope = 'subscription'` declaration. Sections:

1. Parameters (all inputs listed above)
2. Resource Group
3. Managed Identities (`cf-serve`, `cf-runner`)
4. Log Analytics Workspace
5. Key Vault + secret resources + role assignments for `cf-serve`
6. Postgres Flexible Server + private DNS zone + VNet integration
7. Container Apps Environment (VNet-integrated, Log Analytics wired)
8. Container Apps Job `runner` (manual trigger, `cf-runner` identity)
9. Container App `cronfoundry` (public ingress, `cf-serve` identity, Key Vault refs as secrets, env vars)
10. Outputs: Container App FQDN, Key Vault name, Postgres server name

## GitHub Actions Workflows

### `ci.yml` — PR gate

Triggers on `pull_request` targeting `main`.

Steps:
1. `go vet ./...`
2. `go test ./...` — spins up Postgres 16 via `services:` container; uses `internal/testdb`
3. `golangci-lint` via `golangci-lint-action`
4. `cd web && npm ci && npm run build` — verifies React bundle builds cleanly
5. `docker buildx build --platform linux/amd64,linux/arm64 .` — build only, no push; confirms multi-arch compiles

Uses only `GITHUB_TOKEN` — no external secrets required.

### `release.yml` — release workflow

Triggers on tag push matching `v*`.

Steps:
1. Same build + test + lint steps as `ci.yml` (no shortcuts)
2. `docker buildx build --push --platform linux/amd64,linux/arm64 \`
   `-t ghcr.io/gambtho/cronfoundry:{tag} \`
   `-t ghcr.io/gambtho/cronfoundry:latest .`
3. Create GitHub release:
   - Title: `{tag}`
   - Body: auto-generated from commits since previous tag (`gh release create --generate-notes`)
   - Attachments: `deploy/main.bicep`, `deploy/params.example.json`

Uses `GITHUB_TOKEN` for GHCR push (package write permission) and release creation. No extra secrets required.

## Bootstrap & First-Run

After `az deployment sub create --location eastus -f deploy/main.bicep -p params.json`:

1. All Azure resources provisioned. Container App pulls image from GHCR and starts.
2. `cronfoundry serve` startup sequence:
   a. Reads Key Vault secrets via `cf-serve` managed identity.
   b. Runs Postgres migrations (embedded goose, already implemented).
   c. Checks for existing org row. If none, creates one named from `CF_ORG_NAME` env var (default: `"default"`).
3. Operator opens the Container App's public FQDN (output from Bicep), logs in via GitHub OAuth.
4. Clicks "Connect repo" → installs GitHub App on their repo (P3c flow).
5. Pastes LLM API key and any destination secrets via the Secrets page (P3c).
6. First scheduled run fires automatically on the configured cron.

No manual `admin init` or `admin connect-repo` CLI steps required for the Azure path. The CLI commands remain available for local/docker-compose use.

## Upgrade Path

To upgrade to a new CronFoundry version:

```bash
# Update imageTag in params.json, then:
az deployment sub create --location eastus -f deploy/main.bicep -p params.json
```

Bicep is idempotent — re-running updates the Container App image tag and applies any new resource config without recreating resources. Postgres migrations run automatically on startup.

## Operator Setup Guide (`deploy/README.md`)

Covers:
1. Prerequisites: Azure CLI, active subscription, `az login`
2. GitHub App registration steps (permissions required: contents RW, issues W, metadata R; webhook events: push, installation)
3. GitHub OAuth App setup (same App, OAuth tab)
4. Filling in `params.json`
5. Deploy command
6. Post-deploy: navigate to FQDN, login, connect first repo
7. Upgrade procedure
8. `azd down` equivalent: `az group delete -n rg-cronfoundry-prod` (with warning about data loss)

## Testing

- **Bicep validation:** `az bicep build -f deploy/main.bicep` in CI to catch syntax errors (no Azure subscription required).
- **Integration:** Manual smoke test against a real Azure subscription using the P2 smoke-test runbook pattern (`docs/guides/smoke-test-p4.md`).
- **CI workflows:** Validated by opening a PR and pushing a test tag to a fork.

## Success Criteria

A self-hoster can:
1. Clone the repo, fill in `params.json`, run one `az deployment` command.
2. Navigate to the output FQDN, log in, connect a repo, and see their first run fire.
3. Upgrade by bumping `imageTag` in `params.json` and re-running the deploy command.
4. Find the Bicep template and params example attached to any GitHub release.
