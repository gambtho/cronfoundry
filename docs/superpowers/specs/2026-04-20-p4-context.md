# P4 — Azure Deployment — Context & Open Questions

**Status:** Shipped (071966b)

**Target reader:** whoever picks this up after P3 (or whoever wants to deploy cronfoundry to Azure before P3 ships).

## Scope (from master design doc)

P4 moves cronfoundry from "runs on my laptop with docker-compose" to "runs on Azure with a one-command deploy." The master design is explicit about what that means:

- **Bicep template** at `deploy/main.bicep` that a self-hoster can `az deployment sub create` against a fresh subscription
- **Container Apps Environment** hosting the `cronfoundry` service + `runner` as a separate Container Apps Job
- **Postgres Flexible Server** (B1ms burstable, private endpoint, no public access)
- **Azure Key Vault** replacing the envelope-encrypted Postgres secret store
- **Managed identities** — three distinct ones, least-privilege role assignments
- **Log Analytics** wiring via Container Apps' built-in integration
- **GHCR image publishing** — multi-arch container images pushed on merge to `main`
- **GitHub Actions CI** — PR gate (build + test + vet) and release workflow (tag + publish)

## What P2 has already pre-staged for P4

The `internal/cloud/` package exists specifically so P4 can slot in Azure implementations without touching application code:

- `JobDispatcher` interface — P2 has `SubprocessDispatcher`; P4 adds `ContainerAppsJobDispatcher`
- `SecretStore` interface — P2 has `EnvelopePostgresStore`; P4 adds `KeyVaultStore`
- `InstallationCache` + `Signer` are already HTTP-friendly (no local-only assumptions)
- `/internal/*` API is already designed for over-the-wire use between scheduler and runner
- `cronfoundry serve` binds to a configurable `--addr` — just change to `0.0.0.0:8080` behind Container Apps ingress

What P4 needs to add that isn't pre-staged:
- Bicep / ARM deployment templates
- CI/CD (GitHub Actions)
- Managed identity wiring
- Azure SDK imports for Container Apps Jobs + Key Vault

## Key architectural decisions inherited from P2

Non-negotiable constraints that P4 must respect:

1. **Runner runs as a fresh container per fire.** The `JobDispatcher` interface is explicit about this. `SubprocessDispatcher` spawns `/proc/self/exe`; `ContainerAppsJobDispatcher` starts a Container Apps Job with the runner image.

2. **API is long-lived.** `cronfoundry serve` is a Container App (always-on), not a Job.

3. **Scheduler is in-process with API.** P2 chose to collapse scheduler + API into one `cronfoundry serve` binary. P4 keeps them in one Container App, one replica (leader-elected if scaled, but scale-to-one is fine for MVP).

4. **Managed identities, not passwords.** Container Apps uses managed identities to pull from ACR and authenticate against Key Vault. Postgres auth via Entra ID is also available and preferred over password auth.

5. **Private networking by default.** Postgres has no public endpoint; it's in the Container Apps Environment's VNet. Key Vault uses private endpoints or firewall rules scoped to the CAE's outbound IP.

6. **Log Analytics is the log destination.** Container Apps' built-in integration handles it; we don't ship logs ourselves.

## Open questions (a brainstorming session should settle these)

### 1. Bicep vs. Terraform vs. azd

Options for IaC:

- **Pure Bicep** (`az deployment sub create -f main.bicep -p params.json`) — Microsoft-native, one file type, good Azure Portal integration, deployable from any machine with Azure CLI
- **Azure Developer CLI (`azd up`)** — wraps Bicep with a nicer DX for the "clone the repo, deploy it" story. Adds a `azure.yaml` manifest.
- **Terraform** — portable across clouds (P-next ambition), but two tools to learn for a single-Azure deploy

My lean: **Bicep + azd wrapper**. Bicep is the authoritative source of truth; azd gives self-hosters a single `azd up` command. If we later add AWS/GCP, we'd switch to Terraform — but that's a P-way-later concern.

### 2. Container Apps Jobs vs. regular Container Apps for the runner

The master design says Jobs; no ambiguity there. But:

- Jobs charge per-execution (per-second billing of vCPU × memory). Cheap for bursty workloads.
- Regular Container Apps scale-to-zero is also available but has cold-start and per-request billing.
- Jobs have a max duration of 7 days; fine for our 10-min-to-1-hr runs.
- Jobs are spawned via ARM REST or the Azure SDK. The `ContainerAppsJobDispatcher` will use `github.com/Azure/azure-sdk-for-go/sdk/resourcemanager/appcontainers/armappcontainers` (SDK name may differ).

### 3. Key Vault swap-in

The `SecretStore` interface is clean; P4 adds a new implementation:

```go
// internal/cloud/azure/keyvault.go
type KeyVaultStore struct {
    client *azsecrets.Client
    // ...
}

func (s *KeyVaultStore) Get(ctx context.Context, name string) (string, error) { ... }
// etc
```

The Azure SDK for Key Vault (`azsecrets`) is already a transitive dep of our Azure-OpenAI adapter; we'd just need to import it directly.

Open question: do we keep the envelope-encrypted Postgres store as a fallback for local dev (P2 use case) while Key Vault is prod? **Probably yes** — makes `docker-compose dev` work without an Azure subscription.

### 4. Managed identity assignments

Master design specified 3 identities: `cf-api`, `cf-scheduler`, `cf-runner`. Since P2 collapsed scheduler into the api binary, we probably have 2: `cf-serve` and `cf-runner`.

- **`cf-serve`** (Container App) — needs:
  - `KeyVaultSecretsUser` on the Key Vault
  - `KeyVaultCertificateUser` if we later store the GitHub App PEM there (recommended)
  - Postgres contributor / read-write on the DB
  - Container Apps Jobs dispatcher (`Microsoft.App/jobs/executions/write`) for spawning runners
- **`cf-runner`** (Container Apps Job) — needs:
  - Outbound-only (GitHub, LLM providers, destinations)
  - No direct Azure credentials — gets everything via `/internal/*` API call

### 5. Image build + publish

- Single Dockerfile for both serve and runner — they're the same binary (`cronfoundry serve` vs. `cronfoundry runner`)
- Multi-arch (amd64 + arm64 so Apple Silicon devs can pull)
- Published to GHCR; P4 adds a GitHub Action for `release.yml` that:
  - Triggers on tag `v*`
  - Builds multi-arch
  - Pushes to `ghcr.io/gambtho/cronfoundry:v0.3.0-p4` (or similar)
  - Attaches the Bicep template + a sample params file as release artifacts

### 6. CI/CD

PR workflow:
- `go vet`, `go test ./...`, `golangci-lint`, `make e2e` (if docker available in CI runners)
- Build image (don't push)

Release workflow:
- Tagged: build multi-arch + push to GHCR
- Write release notes from commit log since previous tag
- Upload IaC artifacts

### 7. First-run bootstrap story

After `azd up`:

1. Bicep provisioned resources: Postgres, Key Vault, Container Apps Environment, ACR, managed identities
2. Container App `cronfoundry` boots with `serve` — but migrations haven't run and no org is seeded
3. Migration is currently a startup step in `serve`. Do we:
   - Run `admin init` as a sidecar Container Apps Job once, then start `serve`? (cleaner separation)
   - Have `serve` auto-run migrations + seed the default org on cold start? (simpler bootstrap but convolutes `serve`'s concerns)

My lean: **self-serve migrate on startup** for P4. It's what P2 does today. Seeding: if `GetFirstOrganization` returns no rows, `serve` creates one named from an env var (defaulting to `"default"`).

### 8. Public ingress + auth

Container Apps ingress is optional (public, internal, or disabled). For P4 MVP:

- If P3 UI hasn't shipped: `cronfoundry serve` ingress stays **internal** — only reachable from the CAE's VNet. Operators SSH into a jumpbox or port-forward via Azure CLI.
- If P3 UI has shipped: ingress is **public**, behind Azure Front Door (with WAF), TLS terminated there. Session auth takes over from there.

Order of operations matters — if P4 ships before P3, the UI story is "private-only until P3". Document clearly.

### 9. Cost target

Master design: idle/light-use cost < $90/month. Estimated breakdown:

- Postgres B1ms: ~$25/mo
- Container Apps Environment (Consumption + Workload Profiles): $0 baseline
- ACR Basic: ~$5/mo
- Key Vault Standard: negligible
- Log Analytics: free tier ample for small deploys (5 GB/mo)
- Compute: $20-30/mo for light scheduled load (Container Apps Jobs bill per vCPU-second)

Total: **$50-60/month at idle**; headroom under the $90 target.

### 10. Blast radius of destructive IaC operations

- `az deployment sub create --mode Complete` against a shared subscription is dangerous. Bicep deploys should be scoped to a dedicated resource group: `rg-cronfoundry-{env}`.
- `azd down` deletes the resource group. Document this clearly.

## Suggested plan decomposition

P4 is tractable as one plan (~25-35 tasks), but could split if the Azure SDK work drags:

- **P4a — Cloud abstractions: Azure implementations.** `ContainerAppsJobDispatcher`, `KeyVaultStore`, managed-identity wiring for Postgres + KV. Unit-tested against Azure emulators or recorded fixtures. ~10 tasks.
- **P4b — IaC + CI/CD.** Bicep template, azd manifest, GitHub Actions workflows for PR + release. Multi-arch container build. ~10 tasks.
- **P4c — Operational docs + smoke test.** P4 smoke-test runbook (like P2's but for Azure), cost-observability setup notes, GHCR publish walkthrough. ~5 tasks.

Each sub-plan is shippable independently. P4a gives you a cronfoundry you can run on Azure if you deploy resources manually. P4b adds the one-command deploy. P4c makes it documented enough for someone else to use.

## Estimated size

Similar to P2c in scope. **3-4 PRs, 2-4 days of wall-clock time** at P2's pace — with the caveat that Azure SDK integration testing may slow iteration (need an Azure subscription to actually validate) or require heavy mocking.

## Dependencies

- **P2 must be merged.** P2d's shared `internal/testdb` isn't strictly needed, but the `cloud` interface contracts are.
- **An Azure subscription for integration testing.** CI can use a dedicated subscription with a service principal; local dev can use a developer subscription.
- **`golangci-lint`** if not already in CI from P2d.

## What does NOT need to change

- `cmd/cronfoundry/serve.go` — reads config from env; P4 just sets different env values
- `internal/scheduler/*` — untouched
- `internal/api/*` — ingress is external (loopback vs. Container Apps), behavior identical
- `internal/db/*` — Postgres is Postgres; Flexible Server is compatible
- `internal/token/*` — JWT signing is untouched
- Database schema — no changes expected

## Pre-P4 recommended homework

Before starting P4:

1. **Stand up a personal Azure sandbox** so you can iterate without sharing state with colleagues.
2. **Prototype `ContainerAppsJobDispatcher.Dispatch`** against a hand-provisioned Container Apps Job. Confirms the SDK shape (which evolves across Azure SDK minor releases) before committing to a plan.
3. **Decide the Bicep vs. azd question** with one-page brainstorm.
4. **Set up a GHCR namespace + PAT** for image pushes; the `release.yml` workflow needs it.
