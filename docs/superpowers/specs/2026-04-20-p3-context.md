# P3 — Web UI — Context & Open Questions

**Status:** Shipped (e74e651)

**Target reader:** whoever picks this up after the P2 work cools. Assumes familiarity with the master design doc but not day-to-day context.

## Scope (from master design doc)

P3 adds the **read-only operator dashboard + minimum writes** layer on top of the P2 service. Specifically:

- React + Vite + TypeScript frontend served as a static bundle from the API container
- shadcn/ui on Radix + Tailwind for the component library (deliberate choice to avoid generic-AI-dashboard aesthetic)
- TanStack Query for server state
- **GitHub OAuth login** via the same GitHub App's OAuth client (reuses the App we register in P2)
- `admin` and `viewer` roles; allowlist of GitHub logins / org slugs from config
- Read-only views: connected repos, skills + schedules, run history, per-run timeline + log tail
- **Write surfaces (minimum):**
  - Connect / disconnect repos
  - Create / rotate / delete secrets (values never read back after creation)
  - Pause / resume schedules (runtime flag; YAML still source of truth for the rest)
  - Run-now button (triggers a manual run)

## What's already done (reused from P1/P2)

The UI isn't starting from zero — a lot of the contract work is in place.

| Piece | Status | Where |
|---|---|---|
| Secret store (write-only from API, metadata-only reads) | ✅ P2a | `internal/secretstore/` |
| Run history + events timeline (Postgres) | ✅ P2c | `run`, `run_event` tables |
| Manual-trigger endpoint | ✅ P2c | `POST /internal/schedules/{id}/run-now` |
| Schedule pause via `enabled` flag on the row | ✅ P2a schema | (needs a new API endpoint + query; trivial) |
| Admin CLI parity (`list-schedules`, `list-runs`) | ✅ P2a/b/d | `cmd/cronfoundry/admin_*.go` |
| Repo-connection management | ✅ P2b | `admin connect-repo`, `admin list-connections` |

What the UI adds that doesn't exist yet:
- Session auth (GitHub OAuth + signed cookie)
- Per-user-role access control
- Websocket or SSE for live-tail log streaming (optional — polling works)
- HTML admin views of all the CLI-exposed data

## Key architectural decisions inherited from P2

These are non-negotiable and constrain the P3 design:

1. **GitOps is the source of truth** — the UI is read-only for schedule config. Schedule cron, destinations, writeback config, env vars all come from `cronfoundry.yaml` in the repo. The UI can display them but can't edit. (Exception: `enabled` flag, which is a DB-only runtime concern.)

2. **`/internal/*` is runner-facing** — the existing P2c API is not for browsers. P3 needs a NEW namespace, probably `/api/*`, with session auth instead of per-run bearers. The two namespaces can share the same `http.ServeMux` but don't share handlers.

3. **Secrets API writes only** — the API never returns secret values to the UI. P3 must surface this clearly: "rotate" means paste-a-new-value, not view-and-edit.

4. **Single-tenant schema, multi-tenant ready** — every table has `org_id`. P3 should scope all UI queries to the user's org (currently there's only one), so multi-tenant is additive later.

5. **Localhost-only by default** — `cronfoundry serve` binds 127.0.0.1:8080. Opening the UI to the LAN needs either `--addr 0.0.0.0` + TLS + reverse proxy, or a local browser session. P3 probably ships with `--addr 127.0.0.1` and assumes the operator runs the browser on the same host; later phases can harden this.

## Open questions (a brainstorming session should settle these)

### 1. Auth model

- GitHub OAuth (our App already has OAuth client credentials) is the canonical choice — one login mechanism, reuses an existing integration
- Allowlist format: flat list of GitHub logins? List of org slugs (members get access)? Both? Config file vs. DB table?
- Session storage: signed cookies (stateless) vs. DB-backed sessions (revocation)? Cookies are simpler; revocation needs a session table
- MFA: not our concern — GitHub handles it; if a user's GH account has MFA enforced, our OAuth flow picks it up

### 2. Live-tail story

The P2 event model persists events synchronously; the UI could poll or stream.

- **Polling**: simplest. TanStack Query refetches every 1-2 seconds. Works fine for a single operator watching a single run.
- **SSE**: native browser support, one-way stream, good fit. Requires adding an SSE endpoint to the API.
- **WebSockets**: more complex; lets us multiplex multiple runs on one connection. Overkill for single-operator dashboards, right fit for multi-tenant later.

My lean: **polling for P3 MVP, SSE if polling feels sluggish**. Skip WebSockets entirely until multi-tenant.

### 3. Schedule pause/resume UX

Schedule rows have `enabled` boolean. Toggling it via UI is the one "runtime" write against schedule state. Questions:

- Does flipping it persist across repo syncs? (Answer: yes — sync only updates *schedule body*, not `enabled` flag.)
- What about a `pause_reason` column for audit? Or just rely on `audit_log`?
- Does the UI show disabled schedules hidden by default, or greyed out with a "paused" badge?

### 4. Connected-repo UX

Users connect repos via `admin connect-repo` today. The UI equivalent should:

- Show the "Install GitHub App" button that pops open `https://github.com/apps/<appname>/installations/new`
- After callback, list installations → user picks repos → one-click connect

That OAuth callback flow is new territory — needs a `/oauth/callback` endpoint.

### 5. Image packaging

Shipping a React bundle means the CronFoundry container needs to serve static files. Options:

- Serve from the Go binary using `embed.FS` (keeps one container, one deploy)
- Nginx sidecar (two containers, one for API, one for static)
- CDN (Azure Static Web Apps style; requires separate public origin)

My lean: **embed.FS** — simplest, no extra infra, OK for P3's traffic patterns. CDN is a P4+ concern when we have public traffic.

### 6. Framework specifics

- **shadcn/ui** is the right call — components you own, tailwind styling, accessibility built in. Matches the master design's "avoid generic AI dashboard" goal.
- **Vite** over Next.js — this is a client-rendered dashboard, no SSR needs, no routing complexity beyond a few pages. Vite + React Router is lean.
- **TanStack Query** is the right server-state layer. No Redux, no Zustand needed.
- **Type-sharing**: we can generate TypeScript types from our Go structs via tygo or similar. Decide in the brainstorm whether the complexity is worth it vs. hand-maintaining a small types file.

### 7. OAuth callback + CSRF

- We need a public-ish endpoint for the OAuth callback. Either:
  - Binds 0.0.0.0 in production (with TLS)
  - Uses localhost + browser same-origin for development
- CSRF: double-submit cookie pattern on mutating endpoints; same-site cookies help but aren't sufficient alone
- Session fixation: rotate session cookies on login success

## Suggested plan decomposition

If P3 is too big for one plan (~30-40 tasks), split into:

- **P3a — Human auth + session layer.** OAuth flow, allowlist lookup, session cookies, `/api/me`, role-based route guards. ~10 tasks.
- **P3b — Read-only dashboard.** Connected repos, schedules, run history + detail views. Static-bundle packaging. ~12 tasks.
- **P3c — Write surfaces.** Pause/resume, secret rotate, run-now, repo connect. ~10 tasks.
- **P3d — Polish + live-tail.** SSE for in-flight runs, dark mode, keyboard shortcuts, responsive layout. ~8 tasks.

Each sub-plan is shippable independently; you could stop after P3b and have a useful read-only dashboard.

## Estimated size

If you applied the same pace as P2 (subagent-driven, 1-2 tasks per dispatch), P3 is probably **4-6 PRs** and **3-5 days of wall-clock time**.

## Dependencies

- P2 must be merged (including P2d's shared `internal/testdb` — some UI tests will boot Postgres)
- OpenAPI / type codegen tooling: pick during P3a brainstorm

## What does NOT need to change in the existing codebase

- `internal/api/*` handlers (runner-facing) — P3 adds a parallel `/api/*` namespace
- `internal/scheduler/*` — untouched
- `internal/runner/*` — untouched
- `internal/cloud/*` — untouched
- Database schema — UI queries use existing tables; no new columns expected for MVP
